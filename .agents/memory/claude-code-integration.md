# Claude Code 連携（Step 5）

**このプロダクトの差別化点。** Step 4 の設計判断に影響するため、
Step 4 の要件整理に入る前にこのファイルを読む。

## 何を作るか

Claude Code との対話でトレーニング計画を立て、その結果を API へ書き込む。

```
1. ユーザーが Claude Code に相談する
     「先週の結果を見て、今週のメニューを組んで」
2. Claude Code が API から前週の実績を取得する（/analytics/*）
3. 対話しながら計画を作る
     - ダイエット向けの種目・頻度
     - ビッグ3を伸ばすための週3〜4回のローテーション
     - 前週の経過を踏まえた漸進的な負荷設定
4. Claude Code が API へ計画を書き込む（新しい書き込みエンドポイント）
5. モバイルアプリを開くと、今週の予定が下書きとして入っている
     → ユーザーは実行しながら編集するだけ
6. 管理画面で計画と実績の差分・推移を見る
```

## なぜやるか

既存のトレーニングアプリは「AI と一緒にトレーニング方法を考える」体験が弱い。
できたとしても有料プランに閉じ込められていることが多く、
**Claude Code のサブスクリプションを持っている人がその恩恵を受けられない**構造になっている。

そこを解くプロダクトにする。作者自身が真っ先に欲しいものであることが出発点。

## 現行アーキテクチャとの衝突（重要）

**現在の同期は「モバイル → D1 の一方向・全置換」。このままでは Claude Code の書き込みが消える。**

```
現状: POST /backup が D1 の全テーブルを DELETE → INSERT で置き換える

  Claude Code が D1 へ計画を書く
        ↓
  ユーザーがモバイルアプリでバックアップを実行
        ↓
  端末内 SQLite の内容で D1 が全置換され、計画が消える
```

Step 5 に進むには、同期モデルの変更が避けられない。取りうる方向。

- **差分同期にする** — 更新時刻ベースのマージ。競合解決の設計が要る
- **書き込みの向きを分ける** — 計画は D1 が正、実績は端末が正、として
  テーブル単位で所有者を決める。全置換の対象から計画テーブルを外す
- **D1 を正データにする** — オフライン優先を弱める。今の設計思想と衝突する

現時点では2つ目（テーブル単位で所有者を分ける）が最も影響範囲が小さいと見ているが、
Step 5 の設計時に改めて検討する。

## データモデルへの影響

- `workouts.status` は現在 `active` / `completed` の2値。**`planned` を足す**必要がある
- 計画の出所（人が作ったか Claude Code が作ったか）を持たせるか要検討
- 計画と実績の差分を見せるなら、予定セットと実績セットを区別する仕組みが要る
- これらは Step 4 のテーブル再構築（`user_id` 追加・外部キー・インデックス）と
  **同じ移行にまとめられる可能性がある**。Step 4 の設計時に Step 5 の要件を織り込む

## API への影響

現在の API は `/backup`（全置換）と `/analytics/*`（読み取り専用）しかない。
Claude Code から使うには**粒度の細かい書き込みエンドポイント**が要る。

- 計画の登録・更新・削除
- 冪等性（同じ週に対して2回書いても壊れない）
- 検証（存在しない種目 ID を弾く、など）

## クライアントが3つになる

Step 4 の認証設計は「モバイル」「ブラウザ」の2経路を前提にしているが、
**Claude Code が3つ目のクライアント**として加わる。

| クライアント | 認証手段の候補 |
|---|---|
| モバイル | Google ID トークン |
| ブラウザ（管理画面） | Cloudflare Access |
| **Claude Code（CLI）** | API トークン / Cloudflare Access のサービストークン |

CLI はブラウザリダイレクトを持たないため Access は使いにくい。
**ユーザー単位のトークン**を発行して `users` に紐付ける形が素直。
Step 4 の `users` テーブル設計時に、この列（またはトークン用テーブル）を検討しておく。

書き込む先は「そのトークンの持ち主のデータだけ」。
Step 4 のスコープ適用（`user_id` で絞る）がそのまま効く形にする。

## 連携方式の選択肢

- **HTTP で直接叩く** — Claude Code から `fetch` / `curl`。最も単純
- **MCP サーバーにする** — ツールとして提供。対話の中で自然に呼べる。
  Cloudflare には Agents SDK など MCP サーバーを Workers 上で動かす手段がある

どちらにするかは Step 5 で決める。まずは HTTP で成立させてから MCP を検討する順が安全。

## Step 4 で決めておくべきこと

このファイルの内容を踏まえ、Step 4 の要件整理では次を織り込む。

1. `users` に CLI 用トークンを持たせるか（別テーブルにするか）
2. `workouts.status` に `planned` を足す前提でテーブル再構築を設計する
3. 全置換バックアップをユーザースコープ化する際、
   **将来テーブル単位で所有者を分けられる構造**にしておく
