# エラーとログ

**エラーは「利用者に何が起きたか伝わる」「開発者が後から原因を追える」の2つを満たして初めて処理したと言える。**
throw しただけ、catch しただけでは、どちらも満たさないことがある。

## 握りつぶさない

`catch` したエラーを **ログも出さず・throw もせず** 既定値の返却で黙過するのは禁止。
障害時に「何が起きたか」がどこにも残らない。

```ts
// NG
try { await db.execAsync(ddl); } catch { /* 握りつぶし */ }

// OK
try {
  await db.execAsync(ddl);
} catch (error: unknown) {
  console.error('[db] schema 適用に失敗', error);
  throw error;
}
```

無言の `catch` が許されるのは、**パースのフォールバックが目的で、
壊れた入力が想定内**の場合だけ。判断基準は「その catch を通った事実が障害調査で必要になるか」。

```ts
// OK（壊れた設定値は既定へ落とす。ここを通っても調査は要らない）
try {
  const parsed: unknown = JSON.parse(raw);
  ...
} catch {
  return DEFAULT_REST_PRESETS;
}
```

## 文脈を付けて投げる

SQLite や D1 のエラーをそのまま再 throw すると、どの操作が失敗したか上位で分からない。

```ts
// NG
await db.runAsync(sql, params);   // 失敗時にどのクエリか不明

// OK
try {
  await db.runAsync(sql, params);
} catch (error) {
  throw new Error(`addSet failed: ${error instanceof Error ? error.message : String(error)}`, {
    cause: error,
  });
}
```

`cause` を使えば元エラーのスタックも保持される。**握りつぶさずに包む。**

## 失敗しても止めないもの／止めるもの

すべての失敗を同じ重さで扱わない。**記録できないことと、付随機能が動かないことは別問題。**

| 失敗 | 扱い |
|---|---|
| 記録の保存、スキーマ適用、認証 | 止める。ユーザーに伝える |
| 通知音・振動・ローカル通知の登録 | 止めない。ログだけ残す |
| 認証の副作用（`last_used_at` 更新、プロフィール補完） | 止めない。認証は通す |
| 送信（同期） | 止めない。キューに残して再試行し、未送信件数で伝える |

止めない側でも**ログは残す**。無言で機能が欠けるのが一番たちが悪い。

## ユーザーへ伝える

- 同期の失敗はユーザーに見える形で伝える。無言でリトライだけして黙らない
- 認証失敗は `401`、認可失敗は `403`。**どのチェックで落ちたかをレスポンスに書かない**
  （[auth.md](auth.md)）
- 画面のエラー表示は、次にとる行動が分かる文にする。「エラーが発生しました」で終わらせない

## ログに何を書くか

- **トークン・メールアドレス・`sub`・トレーニング記録の中身をログへ出さない。**
  リポジトリは public で、ログは第三者の目に触れうる
- 出すのは「どの操作が」「なぜ」失敗したか。ID は出してよいが、値そのものは出さない
- `console.error` は問題に、`console.log` はそれ以外に使う

## Cloudflare Workers でログを残すには

**`observability.enabled` が true でなければ、`console.error` は Workers Logs に残らない。**
`apps/api/wrangler.jsonc` で有効にしてある。この設定を外さない。

さらに注意点がある。

- **Worker がクラッシュすると、その時点で実行が止まる。**
  CPU 時間超過やメモリ枯渇では `console.error` に到達する前に落ちるため、
  自前のログは残らない。残るのは Cloudflare 側が記録する例外情報だけ
- したがって「落ちる前に必ずログを書く」構造に頼らない。
  **異常系は落ちる前に検知して、通常のレスポンスとして返す**
  （入力の上限、期間の上限、バインド変数の上限を先に検査する。[api.md](api.md)）
- `ctx.waitUntil()` で追跡していない Promise の中で起きたエラーは、
  レスポンス返却後に握りつぶされる。Promise は必ず `await` / `return` / `waitUntil` で追跡する

## React Native 側の注意

- `useEffect` のクリーンアップ忘れは、エラーではなく**多重発火**として表に出る。
  タイマー・購読・イベントリスナは必ずクリーンアップ関数を返す
- 端末のローカル DB はユーザーのトレーニング記録＝代替不能。
  マイグレーションの失敗は握りつぶさず、起動を止めてでも気づかせる

## チェックリスト

- [ ] `catch` の中でログも throw もしていない箇所を作っていないか
- [ ] 再 throw するとき、どの操作が失敗したか分かる文脈を付けたか
- [ ] 止めるべき失敗と、止めなくてよい失敗を取り違えていないか
- [ ] ログにトークン・メールアドレス・記録の中身を書いていないか
- [ ] Promise を `await` / `return` / `waitUntil` のいずれかで追跡しているか
- [ ] 異常系を「落ちてからログで調べる」前提にしていないか
