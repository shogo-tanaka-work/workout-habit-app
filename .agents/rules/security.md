# セキュリティ

3アプリ横断の観点。認証・認可の実装規則は `auth.md`、秘密値の扱いは `secrets.md` にあり、
ここでは再掲しない。この文書は「どの観点で監査するか」と、既存 rules に無い規則だけを持つ。

## 前提（脅威モデル）

- リポジトリは **public**。コードと設定はすべて公開前提で書く
- 守るデータはトレーニング記録・メールアドレス・表示名。ユーザーは少数の知人
- 守る優先度: **① 認可（他人のデータを読み書きさせない）② 秘密値の漏えい ③ 依存経由の侵害**。
  この規模で起きる事故はほぼこの3つに収まる

## OWASP との対応（監査の観点表）

| 観点（OWASP） | 本リポジトリでの担保 |
|---|---|
| アクセス制御の不備（A01 / API1 BOLA） | 行スコープの強制（`auth.md`）。**リクエスト中の userId・オブジェクト ID を信用せず、認証済みユーザーの ID でしか絞らない** |
| インジェクション（A03） | prepared statement の `bind()`（`d1.md`）。テーブル名・列名は呼び出し側リテラルの許可リストのみ |
| XSS | React の自動エスケープ ＋ `dangerouslySetInnerHTML` 禁止（`web-react.md`）。**自動エスケープの外側に注意**（下記） |
| 認証の不備（A07 / API2） | JWT 検証チェックリスト（下記）と fail closed（`auth.md`） |
| 設定ミス（A05） | 認証スキップの抜け道を作らない（`auth.md`）。セキュリティヘッダは roadmap の実装課題 |
| サプライチェーン（2025 A03） | 依存関係の節（下記） |
| 過剰なデータ公開（API3 BOPLA） | レスポンスは必要なフィールドだけ明示的に組み立てる。行やドメインオブジェクトをそのまま `json()` へ渡さない |
| 無制限のリソース消費（API4） | 入力上限の定数（`api.md`）。レート制限は roadmap の実装課題 |
| SSRF（A10） | 外部入力から URL を組み立てて fetch する経路を作らない。必要になったら許可リスト方式にする |
| CSRF | 書き込み API はブラウザから呼ばれない設計（`api.md` の CORS 節）で成立している。**書き込みをブラウザへ開放する変更を入れるときは、先に Origin 検証（`hono/csrf` 相当）を足す** |

## React の自動エスケープの外側

React が守るのはテキストノードと属性値のエスケープまで。次は守られない。

- `href` / `src` など **URL を受け取る属性**。外部入力（ユーザー入力・API レスポンス）を
  URL に使うときは `https:` のみ許可する検証を通す（`javascript:` スキームが通る）
- `dangerouslySetInnerHTML`（使用禁止。`web-react.md`）
- 遷移先をパラメータで受けるリダイレクト（現状は無い。作るなら許可リスト）

## JWT 検証チェックリスト

認証経路を足す・実装やライブラリを変えるときは、この表で照合する（現行実装は
`apps/api/src/auth/`）。

- **署名・`aud`・`iss`・`exp` の4点をすべて検証する。1つも省略しない**
- **`aud` の省略は Access では特に危険。** 同一 Cloudflare アカウントの全 Access アプリが
  同じ鍵で署名するため、`aud` を見ないと**別アプリ向けに発行されたトークンが通る**
- JWKS は team domain の `/cdn-cgi/access/certs` から動的に取得する。
  鍵をハードコードしない（ローテーションで壊れる）
- Google ID トークンは `aud` が自分のクライアント ID、`iss` が `accounts.google.com`
  （`https://` 付きも正）であること
- 検証失敗時の挙動は fail closed（`auth.md` の不変条件）

## モバイルの端末内データ

- **認証トークンを端末に保存しない現行設計を維持する**（`auth.md`）。保存が必要になったら
  `app_settings` や AsyncStorage ではなく `expo-secure-store`（Keychain / Keystore）を使う
- トレーニング記録の SQLite は平文でよい。OS のサンドボックスと端末暗号化に委ねる
  （秘匿性より、機種変更・復元の可用性を優先するという判断）
- ディープリンクは未使用。導入するときは受け取った URL・パラメータを検証してから使う

## 依存関係（npm サプライチェーン）

- **新しい依存を入れる前に確認する**: `postinstall` 等の install script の有無、
  直近の公開履歴（乗っ取り直後でないか）、ダウンロード数と作者。
  ワーム型の攻撃は `npm install` の時点で実行される
- `package-lock.json` をコミットし、再現インストールは `npm ci` を使う。
  lockfile に無いパッケージを増やす変更は、依存追加として上の確認を通す
- 依存を追加・更新する変更セットでは `npm audit` を実行し、結果を確認してから進める
- ライブラリの新規導入自体が方針判断（各アプリの `AGENTS.md`）。この節はその確認内容

## チェックリスト（実装後セルフレビュー）

- [ ] 新しい・変更したエンドポイントはスコープを通しているか（`WHERE user_id = ?` の直書きをしていないか）
- [ ] リクエスト中の ID・ロール・メールを認可判断に使っていないか（使うのは認証結果だけ）
- [ ] レスポンスへ必要なフィールドだけを詰めているか
- [ ] 外部入力が URL・SQL・列名・ログへ達する経路を作っていないか
- [ ] 認証まわりを触ったなら JWT 検証4点セットが揃っているか
- [ ] 依存を触ったなら追加前確認と `npm audit` を通したか
- [ ] `secrets.md` の公開前チェックを実行したか
