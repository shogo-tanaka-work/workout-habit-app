# Cloudflare D1

- SQL は集約する。route の中へ SQL を散らさない
- `SELECT *` を避け、返却に必要なカラムを明示する
- 値は文字列連結せず、prepared statement の `bind()` で渡す
- テーブル名・カラム名へ外部入力を使わない
- 動的 SQL は許可リスト済みの検索条件・並び順・更新項目だけに限定する
- 関連する複数更新は整合性が必要なら `DB.batch()` を使う
- **ループの中で `.run()` を1件ずつ発行しない。** まとめられる書き込みは `DB.batch()` へ
  （横断の原則は [performance.md](performance.md)）
- **D1 は1データベースあたり実質逐次処理。** 1本のクエリの所要時間が DB 全体の
  スループットを決めるため、クエリは短く保つ。クエリ同士を `Promise.all` で並列に
  投げても DB 側で並ぶだけで効果は薄い。削るべきは往復回数（＝ `batch()`）
- リスト取得で N+1 クエリを作らない
- 頻繁に使う WHERE・ORDER BY は `migrations/` の index と照合する
- 新しい・変更したクエリは `EXPLAIN QUERY PLAN` で実行計画を確認する。
  `SCAN`（全走査）が出たらインデックスの張り忘れか、インデックスが効かない形
  （複合インデックスは左端の列から連続して使うときだけ効く）
- 読み取り行数は `.run()` の `meta.rows_read` で確認できる。想定より多ければ過剰取得か
  インデックス未使用を疑う

## D1 固有の制約

- **1クエリあたりのバインド変数は 100 まで**。複数行 INSERT は行数をチャンクに分ける
  （`apps/api/src/backup.ts` の `MAX_BOUND_PARAMS`（90） を参照）
- `DB.batch()` は1回ごとにトランザクションになる。バッチをまたぐ操作は原子的にならない
- 巨大なバッチを積まない（`MAX_STATEMENTS_PER_BATCH` で上限を設ける）
- 件数が不明なクエリの結果を無条件に全件バッファしない

## スキーマ

- スキーマ変更は `migrations/` へ連番SQL（`0002_xxx.sql` …）を足し、
  `npx wrangler d1 migrations apply workout-habit-db --remote` で適用する。
  適用状況は D1 の `d1_migrations` テーブルが持つ
- `apps/api/migrations/` は `apps/mobile/src/db/migrations.ts` と対になる。片方だけ変えない
- 同期対象のカラムを変えたら `apps/api/src/tables.ts` の `SYNC_TABLES` と
  `apps/mobile/src/db/syncTables.ts` の `SYNC_COLUMNS` も同じ変更セットで直す
- 破壊的なスキーマ変更は追加 → 切替 → 削除の段階適用にする
- マイグレーション SQL は適用前に内容をレビューする。本番 D1 へ直接 DDL を流さない
